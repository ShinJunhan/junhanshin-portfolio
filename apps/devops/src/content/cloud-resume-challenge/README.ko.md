# Cloud Resume Challenge

이미 존재하던 사이트에 맞춰 다시 설계한 Cloud Resume Challenge입니다.

원래 과제는 S3에 이력서 페이지를 올리고 CloudFront로 서빙하며 API Gateway 뒤에
방문자 카운터를 두는 것으로 끝납니다. 이 도메인에서는 두 가지 이유로 그 구성이
맞지 않았습니다. `junhanshin.com`의 랜딩 페이지가 이미 이력서 역할을 하고 있어서
두 번째 이력서 페이지를 만들면 같은 일을 하는 표면이 둘이 됩니다. 그리고 이
도메인의 DNS는 이미 Cloudflare에 있고 다른 프로젝트를 서빙하는 중이라, Route 53으로
옮기면 그 프로젝트가 끊기고 이미 가진 존을 중복해서 매달 비용을 내게 됩니다.

그래서 과제를 두 부분으로 나눴습니다. 하나는 이 저장소에 없던 배포 경로입니다. 두
앱 모두 로컬 `dist/` 디렉터리까지만 빌드하고 끝나 있었습니다. 다른 하나는 이 과제를
과제답게 만드는 카운터이고, 지금은 랜딩 페이지 터미널의 `visitors` 명령에
답합니다.

## 무엇을 바꿨고 왜 바꿨는가

| 원래 과제 | 이 프로젝트 | 이유 |
|---|---|---|
| S3 + CloudFront + ACM | Cloudflare Pages | DNS가 이미 Cloudflare에 있고 다른 프로젝트를 서빙 중 |
| Route 53 호스티드 존 | 존을 만들지 않음 | 네임서버를 옮기면 그 프로젝트가 끊기고, 존은 매달 과금됨 |
| 새 이력서 페이지 | 기존 랜딩 페이지 | 이력서 표면이 둘이 되면 서로 경쟁함 |
| API Gateway | Lambda 함수 URL | 리소스가 더 적고, 12개월 뒤 프리 티어가 끝나지 않음 |
| DynamoDB 잠금 테이블 | S3 네이티브 상태 잠금 | Terraform 1.11에서 DynamoDB 인자가 deprecated 됨 |

첫 번째 줄은 조정한 것이 아니라 의도적으로 뺀 요구사항이고, 그 점은 분명히 적어
둘 필요가 있습니다. CloudFront 구성을 직접 만들어 보는 것은 이 과제가 가르친다고
여겨지는 큰 부분이기 때문입니다.

## 배포 경로

`main`에 푸시 한 번이 두 워크플로를 돌립니다.

`pages.yml`은 매트릭스 잡에서 각 앱을 빌드해 각자의 Cloudflare Pages 프로젝트로
배포합니다. `npm install`이 아니라 `npm ci`를 쓰기 때문에 버전은 락 파일이
결정하고, 전이 의존성의 새 릴리스가 배포물을 바꾸지 못합니다.

`infra.yml`은 백엔드를 건드리는 모든 풀 리퀘스트에서 `fmt`, `validate`, `plan`을
실행하고, `main` 푸시에서만 apply를 실행합니다. plan 결과는 잡 요약에 기록되므로
로그를 열지 않아도 변경 내용을 읽을 수 있습니다.

두 워크플로 어느 쪽도 자격 증명을 저장하지 않습니다. Cloudflare는 Pages 범위의 API
토큰을 쓰고, AWS는 OIDC 공급자를 통해 역할을 위임받습니다. 신뢰 정책은 저장소
전체가 아니라 `refs/heads/main`과 `pull_request`를 지정합니다. 포크는 두 주체 어느
쪽에도 닿을 수 없는데, GitHub이 포크가 트리거한 워크플로에는 `id-token: write`를
주지 않기 때문입니다.

## 카운터

터미널의 `visitors` 명령은 Lambda 함수 URL을 호출합니다. 함수는 `ADD` 표현식으로
`UpdateItem`을 한 번 실행하며, 이 연산은 원자적이라 동시에 도착한 두 요청이 하나를
잃지 않고 두 번 증가합니다. 항목을 미리 만들어 두지 않습니다. `ADD`는 없는 항목에
대해 항목을 생성하므로 최초 요청은 1을 반환합니다.

응답은 페이지가 살아 있는 동안 캐시됩니다. 엔드포인트가 요청마다 값을 올리기
때문에, 캐시가 없으면 명령을 다섯 번 실행할 때 방문자가 다섯 명 늘어난 것으로
보고하게 되고 그 숫자는 명령이 스스로 만들어 낸 값이 됩니다.

이 숫자가 재는 범위는 페이지 조회수보다 좁습니다. 터미널을 열고 명령을 입력한
사람을 세며, 그쪽이 더 작고 더 흥미로운 집단입니다.

## 실제 방어선은 어디인가

함수 URL은 공개되어 있습니다. 브라우저 자바스크립트는 요청에 서명할 수 없고, 오리진
액세스 컨트롤을 걸어 둘 CloudFront 배포도 없기 때문에, IAM 인증을 쓰면 호출자가 아예
없어집니다.

이를 막는 것은 CORS가 아닙니다. 허용 목록은 다른 사이트의 스크립트가 응답을 읽는
것을 막을 뿐 `curl`에는 아무 영향이 없습니다. **실제로 유효한 통제는 함수의 예약
동시성**이고, 그 대가는 트래픽이 몰릴 때 실제 방문자가 429를 받는 것입니다.

실행 역할이 가진 데이터 평면 권한은 테이블 하나에 대한 `dynamodb:UpdateItem` 하나
뿐입니다. 함수는 그 테이블을 읽거나 스캔하거나 삭제할 수 없습니다. `logs:CreateLogGroup`도
의도적으로 빼 두었는데, 자기 로그 그룹을 만들 수 있는 함수는 보존 정책 밖의 그룹을
만들 수 있고 그렇게 로그가 조용히 영구 보관되기 때문입니다.

배포 역할의 정책도 관리형 정책을 가져다 쓰지 않고 구문 단위로 직접 작성했습니다. 그
중 위험한 항목은 `iam:PassRole`이며, 역할 하나만 지정해 두는 것이 CI가 계정의 아무
자격이나 Lambda에 넘기지 못하게 막습니다. 대가는 분명합니다. 리소스를 추가하려면 그
액션을 먼저 정책에 넣어야 하고, 빠뜨리면 완전히 올바른 정책을 두고 `AccessDenied`로
apply가 죽습니다.

## 비용

반올림해서 0원이 아니라 계산해서 0원입니다.

DynamoDB는 Always Free 한도 25 대비 읽기 5, 쓰기 5로 프로비저닝했고 오토스케일링은
붙이지 않았습니다. 부하가 걸렸을 때 그 선을 넘게 만드는 것이 오토스케일링이기
때문입니다. Lambda는 영구 프리 티어 안에 있습니다. 로그는 무료 수집 5GB 대비 14일
뒤 만료됩니다. Terraform 상태 버킷은 수 킬로바이트를 담고 이전 버전은 30일 뒤
만료됩니다.

DynamoDB를 온디맨드로 두었다면 이 정도 규모에서 몇 센트의 몇 분의 일이 나왔을
텐데, 그것은 0원이라는 말과는 다른 이야기입니다.

## 아직 하지 않은 것

인프라 코드는 작성하고 포맷하고 검증했습니다. **아직 apply 하지 않았습니다.** 이
페이지에 배포 시간, 실측 비용, 방문자 수가 없는 이유는 그 값들이 아직 존재하지
않기 때문이고, 추정치는 그 값이 아니기 때문입니다.
